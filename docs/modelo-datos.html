Modelo de datos SnapIt

Las cuatro entidades del grupo y las dos que aporta el plugin Users & Permissions, con sus relaciones tal como están definidas en los schema.json del backend.

Diagrama entidad-relación MER

  • PK clave primaria
  • FK clave foránea
  • UQ valor único
  • uno a muchos (1:N)
  • entidad del plugin (no se modela)
  • relación modificada

Modelo relacional MR

categorias (id, nombre, slug, descripcion)
zonas (id, nombre, slug)
incidentes (id, titulo, descripcion, direccion, estado, fecha_apertura, fecha_cierre, categoria_id → categorias, zona_id → zonas)
reportes (id, descripcion, foto, fecha, incidente_id → incidentes, autor_id → up_users)
pluginup_users (id, username, email, password, confirmed, blocked, role_id → up_roles)
pluginup_roles (id, name, type)

Cómo lo guarda Strapi en SQLite

El MR de arriba es el modelo lógico. En la base, Strapi no pone la clave foránea en la tabla: cada relación va en una tabla de enlace propia.

incidentes_categoria_lnk incidentes_zona_lnk reportes_incidente_lnk reportes_autor_lnk up_users_role_lnk files_related_mph

Además agrega a cada tabla document_id, created_at, updated_at, published_at, created_by_id, updated_by_id y locale. La foto del reporte vive en la Media Library y se enlaza por files_related_mph.

Valores cerrados

  • incidente.estado: abierto, en_curso, cerrado
  • role.type: vecino, operador, administrador (más public y authenticated, que trae Strapi)
  • fechaCierre y foto son opcionales

Reporte → User pasó de 1:1 a N:1. Con oneToOne cada usuario podía tener un solo reporte. El cambio está en la rama feature/seed-reportes y hay que consultarlo con el grupo antes de mergearlo.
